# CFD Export Validation (TODO_MODELING.md Step 7)

## Summary

The modeler's export pipeline (`apps/modeler/src/model/exportGeometry.ts` + `stlExport.ts`) had never actually been fed to a mesher. This validates it end-to-end, locally, in Docker: generate the simplest possible model (one room, no doors), export it the same way the app would, mesh it with `snappyHexMesh`, and solve it with `buoyantSimpleFoam` - all at the lowest settings that still produce a usable result. It's a proof that the pipeline works, not a physically-accurate simulation.

**Result: it works.** `snappyHexMesh` meshed the exported STL "without any errors", `checkMesh` reports "Mesh OK", and `buoyantSimpleFoam` ran to completion for 150 iterations with no `FOAM Warning`/`FOAM FATAL` and no NaN/divergence.

## The fixture

`docs/cfd/fixtures/single-room.stl` (multi-solid ASCII) and `single-room-binary.stl` are a single 4m x 3m x 2.5m room, walls 0.15m thick, no openings - the simplest input the exporter can produce. They're generated straight from the model core (not hand-drawn), so they exercise the real export path (`computeExportAirVolume` -> `validateExportMesh` -> `meshToMultiSolidASCIISTL`/`meshToBinarySTL`), just with a scripted project document instead of one built through the UI.

Regenerate them after any exporter change:

```bash
cd src/Aerie.Web/apps/modeler
WRITE_CFD_FIXTURE=1 npx vitest run src/model/cfdFixture.test.ts
```

(`src/model/cfdFixture.test.ts` is skipped by default - normal `npm test` runs never write to disk - and only runs when `WRITE_CFD_FIXTURE=1` is set.)

The resulting STL's interior bounding box is `x:[0.075,3.925] y:[0.075,2.925] z:[0,2.5]` (room minus the 0.15m wall thickness on each side, per `exportGeometry.ts`'s negative-space export), with three named solids/patches: `walls`, `floor`, `ceiling`.

## The OpenFOAM case

`docs/cfd/case/single-room/` is a complete, ready-to-run OpenFOAM case built around that STL:

- `constant/triSurface/single-room.stl` - copy of the fixture above.
- `system/blockMeshDict` - a coarse background box (`11x8x7` cells) comfortably containing the STL; `snappyHexMesh` discards everything outside the STL anyway, so this only needs to be big enough, not tight.
- `system/snappyHexMeshDict` - lowest-effort settings: `castellatedMesh` + `snap` only (`addLayers false`), refinement level `(0 0)` everywhere, no explicit feature-edge snapping. The three STL solids are mapped to boundary patches of the same name via `geometry.regions`.
- `constant/{g,thermophysicalProperties,turbulenceProperties}`, `system/{controlDict,fvSchemes,fvSolution}`, `0/{T,U,p,p_rgh,alphat,k,nut,omega}` - adapted from OpenFOAM's own `buoyantSimpleFoam` tutorials (`$FOAM_TUTORIALS/heatTransfer/buoyantSimpleFoam/buoyantCavity` and `.../airRecirculationRoom`), trimmed to this case's three patches. Floor is fixed at 307.75 K (34.6°C), ceiling at 288.15 K (15°C), walls adiabatic (`zeroGradient`) - an unstable, hot-below stratification, which reliably drives a convection cell instead of sitting stagnant. `endTime 150` with no attempt to fully converge - enough iterations to prove the solver runs stably, not to reach a physically settled answer.

Everything under `constant/polyMesh/` (the generated mesh), numbered time directories (`10`, `20`, ... - the solver's output), and `log.*` are gitignored (see `docs/cfd/case/single-room/.gitignore`) - they're regenerated by the commands below, not checked in.

## Running it

Requires Docker. Uses OpenCFD's official image (`opencfd/openfoam-default:2406`, ~2GB, first pull only).

```bash
cd docs/cfd/case/single-room

docker run --rm --entrypoint bash -v "$PWD":/case opencfd/openfoam-default:2406 -c '
  source /usr/lib/openfoam/openfoam2406/etc/bashrc
  cd /case
  blockMesh
  snappyHexMesh -overwrite
  checkMesh
  buoyantSimpleFoam
'
```

Note the `--entrypoint bash` + manual `source .../etc/bashrc`: the image's default entrypoint (`/openfoam/run`) unconditionally `cd`s to `$HOME` before running anything, silently ignoring `-w`/`--workdir`, so a plain `docker run ... bash -lc '...'` ends up operating on `/root` instead of the mounted case. Overriding the entrypoint and sourcing OpenFOAM's own `etc/bashrc` directly sidesteps that.

Runtime on a laptop: well under a minute total for this mesh size (~380 cells).

## What each stage produced

- **`blockMesh`**: 616-cell background mesh, one patch (`outerBoundary`).
- **`snappyHexMesh`**: "Finished meshing without any errors." 378 hex cells, 3 boundary patches (`walls`, `floor`, `ceiling`).
- **`checkMesh`**: "Mesh OK." Domain bounding box exactly matches the room interior (`(0.075 0.075 0)` to `(3.925 2.925 2.5)`), total volume 25.19 m³, max non-orthogonality 34.8° (well under the 65° warning threshold), max aspect ratio 2.8, max skewness 1.64 - all comfortably within OpenFOAM's default quality bounds.
- **`buoyantSimpleFoam`**: ran all 150 iterations, no fatal errors or warnings, no NaN/divergence. `p_rgh` initial residual dropped from 0.24 (iteration 10) to ~0.06 (iteration 150) - trending down but not fully converged, which is expected and fine at this iteration count; the point was proving the solver runs stably on the exported geometry, not reaching a converged flow field.

## Conclusions for the exporter

- The multi-solid ASCII STL's per-patch naming (`walls`/`floor`/`ceiling`) round-trips cleanly into `snappyHexMesh`'s `geometry.regions` mapping - no manual STL surgery needed between "exported by the app" and "consumed by OpenFOAM".
- `exportValidator.ts`'s watertightness check was predictive: the fixture passed it, and `checkMesh` found zero open/non-manifold geometry issues downstream. That's the intended contract (spec #8: "fail here rather than inside a mesher") actually holding up against a real mesher.
- Not yet exercised: a project with multiple rooms and an open doorway (the bridge/`PATCH_WALLS` carving logic in `exportGeometry.ts`, already covered by unit tests) going through this same Docker pipeline, and a mesh fine enough to draw real conclusions from the solved flow field. Both are natural follow-ups but weren't necessary to answer this step's question (does the exporter's output actually mesh and solve).
